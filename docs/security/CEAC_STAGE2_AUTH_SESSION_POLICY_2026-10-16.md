# CEAC OS — Stage 2 universal authenticator MFA and session-continuity policy
**Owner change:** 16 October 2026. **Binding owner direction, not deployed implementation.** Companion: `docs/continuity/CEAC_STAGE2_UNIFIED_EXECUTION_CONTRACT_2026-10-16.md`.

## The policy that supersedes 12 October's Google-only requirement
1. **Google-only sign-in is CANCELLED** as a Stage 2 requirement. No Google Workspace subscription or exclusive Google provider is necessary. Retain existing invitation/HR-approved CEAC identity lifecycle and **email/password sign-in** (with secure password reset). Google sign-in may be optional later with explicit approval, but cannot be a prerequisite, create arbitrary accounts or modify role authority. No public open-registration or auto-provisioning, no duplicated existing Auth IDs, employee roster or protected HR records. Preserve the email-based active Stage 1 auth until a verified, separately approved cutover.
2. **Every active interactive CEAC user role** (Staff, Manager, Technical Support, HR/Admin, Executive, eligible Volunteer) must enrol a verified **TOTP factor** in a standards-compatible authenticator app (Google Authenticator, Microsoft Authenticator, 1Password, etc.) and present its fresh code to reach **Supabase AAL2** on actual new logins, before protected app data, queries, RPCs, files or actions. Not just Managers/privileged users. No "MFA UI checked" pseudo-security; enforce the session's AAL2 at DB/Auth/Storage and every other relevant server boundary with bounded setup/recovery exceptions. A verified Google login alone cannot substitute for app TOTP.
3. **Avoid repeated codes for ordinary work during the day:** persist and auto-refresh the existing **verified AAL2 session** across navigation, tab refresh, short inactivity, network recovery and valid short disconnects. Do NOT create a new sign-in on a silent token refresh, unit switch or every page load. Correct underlying sign-out/session-refresh defects first. A deliberate explicit sign-out must revoke local session and any applicable refresh token; the next truly new login **must** present TOTP. MFA is also required after genuine expiry/revocation or login on a different device; no localStorage-only boolean, grace clock or UI hiding may bypass the AAL2 database boundary.
4. **Brief accidental sign-out grace** is a UX request, NOT blanket authorisation for weaker authentication. First prevent accidental 5-minute sign-out by session continuity. Investigate a same-device secure resumption mechanism only if needed; propose explicit risk design (short absolute validity, cryptographically bound device/session credential, server revocation/rotation, stolen-token, shared-device, logout and account revocation handling) for separate owner approval and platform validation. Do not implement 'skip code for 12 hours' by local timestamp, assume Supabase AAL2 survives new AAL1 authentication, or call a new session AAL2 unless genuinely verified. If no secure design is available, require TOTP on fresh sign-in and document the UX tradeoff.
5. A remembered verified session is device/browser-specific and never transfers assurance to another device; permission changes, loss/recovery, a terminated or revoked user, suspected account compromise, or changed credentials must invalidate appropriate sessions. MFA factor enrolment and replacement require verified identity and human-audited recovery without a bypass. Use backup/recovery controls that do not lock out the last authorised Administration holder or permit helpdesk impersonation. Apply step-up for especially sensitive actions if required by current capability model.
6. No data-protection exception from an unavailable MFA factor: before AAL2, only Supabase Auth MFA APIs and **narrow, independently secured** enrollment/eligibility/recovery endpoints may be accessible. User-visible errors remain understandable; no private HR/project/Support data pre-enrollment.

## Exact acceptance and negative tests
- New invited active employee: password login → narrow TOTP enrollment → verified challenge → AAL2 → own authorised panel; skip enrollment on next login but still fresh challenge; repeat for all real role types.
- Existing password user retains `auth.users.id`, profile, HR roster, unit memberships, capability grants, audits, working history after adoption; login still works. Uninvited, disabled, expired invite, unconfirmed/revoked identities cannot access or enroll.
- AAL1 attempts to read every protected public/HR/Payroll/Support/finance/work/report route via direct REST/RPC/storage must be denied. AAL2 proper actor permitted; off-tenant/off-unit, revoked capabilities remain denied even AAL2. Test direct API access and JWT method claims, factor revocation.
- Valid AAL2 session across page reload, unit switch, normal Supabase refresh, short inactivity, network loss/recovery stays authorised without code repeat. Explicit logout and truly new session trigger TOTP. Fresh second browser/device never inherits first device MFA. Token expiry and compromised/revoked user must fail closed, no automatic silent account re-enrollment.
- Demonstrate user-facing enrolment/change-device/recovery, no unsupported promises about offline apps, and mobile/desktop app redirects with actual provider security settings.
- Credentials and TOTP seeds NEVER in GitHub, test recordings, issue comments or TinyFish traces; use test accounts and safe redactions.
- Auth stage acceptance requires isolated restored-data migration replay + authoritative real-auth provider testing; source tests alone **cannot certify** provider hooks, session-refresh behaviour or AAL2. Require explicit owner approval before enabling any production Auth hook/provider/MFA policy or disabling an old sign-in route.

## Operational decision
The baseline is *one verified TOTP challenge per genuine new session*, **not one every 5 minutes or every app page**. If the owner later approves an actual 'remember device for the workday' bypass for new sessions, it requires a distinct signed threat model and platform-safe mechanism; until then a fresh login after explicit logout prompts again, while normal persistent AAL2 work does not.
